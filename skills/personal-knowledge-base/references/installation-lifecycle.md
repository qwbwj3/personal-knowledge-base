# 从 GitHub 安装、更新和恢复代码

安装器验证代码来源与能力；代码安装完成不代表宿主自然发现、重新加载与真实资料使用已经通过最终验收。

请把仓库链接交给宿主 Agent，让它通过正常 GitHub 授权克隆 `qwbwj3/personal-knowledge-base-test`，确认发布者给出的完整提交，阅读本页并执行安装。不要在聊天中粘贴令牌。缺少 Python 3 或 Git 时，由宿主通过正常授权准备；本安装器不执行 sudo、全局 pip 或修改宿主配置。

在**干净克隆根目录**执行（Windows 可将 `python3` 换为 `py -3`）：

```sh
python3 -B skills/personal-knowledge-base/scripts/install_workbuddy.py --check --expected-commit <完整40位提交>
python3 -B skills/personal-knowledge-base/scripts/install_workbuddy.py --apply --expected-commit <完整40位提交>
```

默认读取 `WORKBUDDY_CONFIG_DIR`，其次 `CODEBUDDY_CONFIG_DIR`，否则 `~/.codebuddy`，安装到其 `skills/personal-knowledge-base`。隔离试验可以显式 `--target <普通目录>`。不写其他配置。

更新时先由宿主正常 fetch 并切换到已确认的发布提交，再从该干净克隆运行 `--update --expected-commit <完整提交>`。安装和更新共用事务实现；同一提交重复运行会重新检查能力，不重复切换。不要把知识库资料维护的 `update` 与这里的 Skill 代码升级混淆。

### Windows占用与待切换

升级分为“可信候选已准备”和“已在安装位置生效”。受占用或访问权限影响，活动目录可能不能移动；不采取逐文件覆盖、手改收据、强制结束宿主或关闭安全保护的方式。

- `activation_pending`、退出码3：候选已校验暂存、尚未生效，原有版本保留。`pending.id/commit` 是待切换版本；`active` 才是当前安装。请明确告诉用户“还没有升级完成”。再次更新同一提交复用这一份候选，不不断创建副本。
- `recovery_pending`、退出码3：切换中断且恢复也暂时受阻。备份/候选/事务保留，**不能声称旧版已恢复，也暂勿调用Skill**。下一次续装先完成恢复。
- `status/check` 会显示 `requested_commit` 和 `version_matches_request`；仅有ready不能证明已装所选新提交。`--check`还验证实际格式能力。安装在磁盘上完成仍不证明WorkBuddy已经刷新其内存中的旧Skill说明，应正常重新加载并新开对话确认版本。

遇到待切换，由Agent解释并安排一次正常关闭占用程序后的续装：

1. **Windows优先使用独立续装入口**：Agent按返回的 `resume_detached_argv` 结构化参数直接启动，无需用户抄命令。它只启动一次、最多等待300秒（另计校验/能力探针耗时）的安装进程，不创建计划任务、服务，不提权、不关闭安全保护、不kill宿主。
2. 只有返回 `resume_worker_started` 且 `worker.independence_verified=true`，才说明子进程已确认离开宿主的Windows任务对象；这**不代表升级已生效**，退出码仍为3。告诉用户“续装已就绪，请保存工作并正常退出WorkBuddy，稍后重新打开”。具体占用未经现场定位，不仅凭WinError5断言是WorkBuddy锁定。
3. 分离进程使用正常Windows进程创建权限；系统不允许脱离任务对象时明确拒绝，**不能去掉breakaway要求偷偷退回随宿主结束的子进程**。启动未确认时先读结果与错误日志，不连续启动多个等待进程。无法安排独立进程才使用返回的 `resume_argv` 在独立终端前台续装；用户无需编辑JSON或安装目录。
4. 进程在安装管理目录运行，日志也在这里，不从将被移动的技能目录运行。它重读可信Git来源，验证候选/原安装、格式能力，经原有完整事务切换。原件、知识库、OCR环境均不动。
5. 正常重开WorkBuddy后，Agent先读取 `worker.result_path`（结束前可能为空/不完整）与 `stderr_path`，再从可信克隆运行 `--status` 和 `--check --expected-commit <完整提交>`，核对实际生效提交及能力。仅启动记录、PID或进程已退出都不能作为成功证据。重新加载技能说明并新开对话后再验真实宿主交互。
6. 等待超时仍明确为pending，保留候选；释放后仍被拒绝需查目录权限、安全软件或实际占用，不反复复制、不逐文件覆盖、不改收据。

独立续装日志是操作记录，不是安装收据；不会参与来源授权。没有宿主常驻通知机制，最终生效必须在重开后主动核对。嵌套任务对象、权限策略、宿主退出后的实际生存以及桌面加载仍需Windows实机验收；Mac上的模拟测试不能证明这些行为已通过。

```sh
python3 -B skills/personal-knowledge-base/scripts/install_workbuddy.py --resume <待切换ID> --target <原安装目录> --expected-commit <完整提交> --wait-seconds 120
```

`--wait-seconds`仅用于`--resume`，含0在内的显式参数不能用于其他动作。等待期间每次尝试仍有目标级互斥及完整性校验。需要改装另一版本时，先征得用户对目标版本的决定，再执行`--cancel-pending <ID>`；只取消待切换，不删除候选或改动原库。不能偷偷用另一个候选替代用户已选版本。

rc.3在移动失败后留下的完整候选可校验复用。Windows临时“复制覆盖并手改收据”若留下**与生效Git提交完全一致**的重复暂存副本，新版将副本保留到非占用槽位，再走正常事务；任何混合代码、额外文件或不一致收据都拒绝，不能据此批准不完整的手动覆盖。

```sh
python3 -B skills/personal-knowledge-base/scripts/install_workbuddy.py --status
python3 -B skills/personal-knowledge-base/scripts/install_workbuddy.py --rollback <备份ID>
```

更新成功输出的 `backup` 是上一版代码的 ID；`--status` 的 `stored_versions` 包含已保留的版本目录（中断候选也可能保留）。`version_details` 逐ID直接列出提交、是否当前版本、记录有效性（`record_status`）与代码状态（`code_status`：verified/invalid/missing/not_checked），并提供可读说明。损坏或无法核实的记录不会中断其他存储版本的诊断；其中的提交在记录验证前仅是声明值。宿主据此向用户说明后选择，无需用户翻阅或编辑 JSON。status 不执行存储版本能力代码，`capability_checked` 为 false；代码验证通过也不代表可以跳过回滚能力预检。回滚重新验证备份并预检能力，只回滚代码，不回滚知识库当前停用、授权或人工笔记。保留克隆的历史 Git 对象，回滚与恢复需要它们；收据中的旧提交必须是当前所选可信提交的祖先，不接受无关或悬空对象。

无收据目录默认拒绝覆盖。若宿主能从可信历史找到与该目录**文件集合、内容、执行位完全一致**的旧提交，可以使用 `--apply --adopt-commit <旧完整提交>` 接管并升级；不能证明时请用户另选目标，不能自动删除旧目录。未知文件（包括目录内人工笔记）会导致拒绝。

## 可信边界

- 首次运行的 Python 安装入口本身必须来自用户正常授权取得并确认的克隆。任何安装器都不能用自己的检查证明自己未被替换。宿主应在执行入口前确认仓库和发布提交。
- 固定允许的 GitHub origin 防止误用其他仓库或本地镜像；它不是签名验证。正常 GitHub 认证/传输、用户确认的发布提交是来源信任的前提，本地 origin 字符串可以被伪造。
- `--expected-commit` 必须是完整40位提交并与 HEAD 一致；未提供时选择 HEAD。强烈建议宿主传入独立取得的预期提交。Git 对象校验确保全部 Skill 文件和模式匹配所选提交，不证明维护者发布内容安全，也不抵御仓库账号被攻破或本机恶意管理员。
- 验证拒绝缺失、额外文件、符号链接、非普通文件、执行模式变化和暂存区改动。在运行候选能力代码之前完成验证。安装复制 Git 对象，不复制未经核对的工作区内容，复制后以及预检后复核。
- ZIP/散包目前明确不受支持：不要执行包内入口来证明包自身可信。请改用已验证 Git 克隆。包内自生成 manifest 或版本号不是独立信任锚点。未来 ZIP 支持必须从已可信入口接收独立预期原 ZIP 哈希。

## 事务和诊断

管理目录是目标旁的 `.personal-knowledge-base.install-manager`（显式目标则按其目录名命名），不是知识库目录。管理目录、候选、备份与安装目标必须处于同一文件系统，以保证切换 rename 的原子性。源Git克隆可以在其他磁盘：安装从已验证Git对象复制到目标盘上的候选目录，并重新核对内容与模式。路径祖先符号链接、目标非目录、源目标重叠拒绝。目标级操作系统文件锁避免并发写，进程退出自动释放，不扫描进程或 kill。

候选能力检查在所有平台均要求基础格式和真实文本PDF探针通过。宿主在实际运行Skill的Python中安装 `references/pdf-requirements.txt`。OCR属于低频补充，模型默认不下载，不阻断纯文本PDF安装；需要时读 `ocr-runtime.md`，显式prepare并实际识字自检后再更新资料。失败时不切换，返回结构化 `reason/impact/next_step`，依赖缺失不称为数据损坏。

切换前持久记录事务阶段；提交决定持久化之前中断，下次核对候选/旧版并恢复上一版；提交决定持久化后中断，核对后完成新版本提交。完成和回退记录保留，不依赖删除文件结束事务。兼容没有阶段字段的旧中断记录，校验后恢复旧版。`--check/--status` 因此在存在未完成事务时会执行恢复，不是绝对只读。首次安装在提交决定前中断恢复为未安装；提交决定已经持久化后则完成经核验的新安装。一般操作异常会即时尝试恢复。断电时的持久化依赖文件系统支持；Windows rename/锁/持久化只有代码路径，尚无实机结论。

退出码：0 本次代码操作成功；1 尚未安装；2 拒绝或失败；3 已暂存待切换/待恢复，未完成。不要删除管理目录来消除错误。收据和备份被改动会阻止恢复，需宿主检查；当前不提供自动清理历史备份，以免删除用户需恢复的版本。

rc.4事务使用v2日志，读取旧v1和更早中断记录；旧安装器不能解释新待切换阶段。升级、恢复、回滚统一从当前可信克隆运行，不用旧安装内的升级器处理新日志。此日志升级不修改任何知识库数据格式。

代码升级到1.2.0-rc.3后，提示并执行已授权资料的知识库更新，使旧PDF通过新版质量检查、建立固定提取全文。代码回滚保持最新授权/停用控制；若回滚到不识别新提取协议的版本，不将其旧非空解析结果重新宣布质量合格。

新版资料更新会写发布清单v3；新版可读旧v1/v2，但早于本修复的Skill会明确拒绝v3，避免将不同解析历史混用。回滚只回代码、不降级数据；若旧代码拒绝新格式，恢复兼容Skill，不重建/覆盖原库。

## 更新后的资料与Obsidian

从可信新克隆运行升级，不从旧安装内运行旧升级器。完成后执行“更新我的知识库”，在原库中迁移已死亡旧操作的残留状态并补建Obsidian视图，不重建、不清空。未知旧锁或仍在运行的旧进程须先核实；新版保留兼容栅栏，旧版写入器不能再写已迁移的库，代码回滚不降级写入协议。

Obsidian首次打开、路径和用户笔记保护见[浏览流程](obsidian-workflow.md)。Windows WorkBuddy安全删除保护保持开启；安装事务和知识库操作完成均不以删除标记作为条件。

真实PDF能力探针使用代码目录之外的显式临时父目录，不依赖Python“创建后删除才能证明临时目录可用”的默认发现流程。宿主拒绝清理合成探针时，保留文件并单独返回cleanup_warning，不把解析通过改报缺少PDF依赖，不改宿主删除保护。

### 独立续装状态与诊断

分离worker先在数秒内确认进程独立性，再执行可能较慢的Git完整校验；早期握手不授权安装。通过 `worker.progress_path` 读取 starting / verifying / waiting / activated / failed，`worker_finished` 指示本次等待已结束。Windows Git/Python安装子进程静默运行，错误保留日志，不弹反复控制台。等待采用有界退避；对已定位的目录移动拒绝先做轻量访问探测，仍被拒时不重复整库代码校验。探测通过后仍完整验证再切换。

非移动步骤的PermissionError不会伪装成pending：回执 `error.operation/path/errno/winerror` 说明具体读文件、管理记录写入/发布等失败位置。应据此检查实际权限或安全软件，不笼统归因为宿主锁。300秒重试预算不包含完整验证的耗时；单次Git和能力探针各自有超时，不启动永久等待器。
